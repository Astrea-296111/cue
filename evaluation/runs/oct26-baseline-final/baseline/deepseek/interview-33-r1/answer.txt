是的，我直接调了 Claude 和 DeepSeek 的官方 API，通过统一的模型适配层接到我自己的 Agent harness 里做对比，没有经过第三方中转。测试口径是同一套任务、同一套提示词和工具定义，只换模型，所以我认为那次“Claude 最好、Qwen 其次、DeepSeek 当时偏低”是有可比性的。

RAG 我在 agent 项目里没有作为独立模块做，但整体链路我是清楚的，也会这样落地：离线把文档切块、做 embedding 建向量索引，并保留标题、来源、版本等元数据；在线检索先做查询改写或扩展，再向量召回加关键词召回做混合检索，然后重排取 Top-K，把带出处的片段拼进上下文，让模型回答时能引用。工程上我重点看三件事：一是切块和元数据，因为它们直接决定召回质量，块太小丢上下文、太大稀释相关性；二是评估，我会准备一套问题-标准答案-正确文档的集合，分别看召回率和最终答案正确率，而不是只看体感；三是幻觉控制，检索不到就明确说没找到，不硬编。比如问“某商品退换货规则”，先召回对应政策段落再回答，并附上来源；如果只召回到旧版本，就靠元数据过滤掉，避免答过期规则。

在 Agent 场景里 RAG 我更多把它当工具用：让 Agent 自己决定什么时候检索、检索几次，把检索结果作为观察结果回到循环里，而不是每次无脑塞知识，这样能省上下文也减少干扰。如果改用纯长上下文方案，短文档场景够用，但知识更新频繁或文档量大的时候，成本和时效都不如 RAG，我会按数据规模和更新频率来选。

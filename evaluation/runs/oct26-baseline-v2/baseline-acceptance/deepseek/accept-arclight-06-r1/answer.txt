同名工具我会在包装层加服务名前缀，把来自不同 MCP 服务的同名工具映射成对模型唯一的工具名，内部仍保留原始服务名和工具名，执行时按这个映射路由回对应服务；模型看到的 description 和 inputSchema 还是该服务端原始内容，区分靠的是前缀而不是 Schema。比如两个服务都暴露 search，会变成 svc_a__search 和 svc_b__search，调用后者时包装器只把它转给 svc_b 的客户端。

把完整 inputSchema 给模型，不等于 Pydantic 执行时就验证了全部嵌套结构和枚举约束。当前实现是包装器按顶层属性构造 Pydantic 参数模型再交给 MCP 客户端，嵌套对象的约束、枚举取值等要看参数模型是否完整映射了这些约束，而且没设置 strict，隐式类型转换仍可能发生。所以我会把它理解为“模型拿到的是完整 Schema，执行侧是部分约束”：如果确实要严格拒绝非法枚举和深层嵌套，我会在交给 MCP 客户端前按原始 JSON Schema 校验，或开启 strict 并对嵌套模型做完整映射，再用一组越界枚举、深层嵌套错误类型的用例验证是否真的被拒。

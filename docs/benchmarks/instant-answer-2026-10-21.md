## 测量范围与对照

环境：Linux x64、Node v24.19.0、AMD EPYC 9V74，环境可见 5 个 CPU。性能基准不与完整测试/UI/native 任务并跑；CPU 组只另加一个明确的计算 worker。真实 package entry → 语音事件/快捷键或手动文字 → QuestionResolver → 正式目标/预算 → SDK 序列化全部执行；网络模型替换为固定 5ms 本地传输。ASR replay 是已接受事件回放，没有真实语音识别、VAD 音频或 Windows 录音。

**A 的 smart=true 是受控实验配置，不是已证实的用户旧线上配置。** A 的悬挂语义场景包含标准深度等待，不能将其约 200ms 的局部结果当作用户 fast 模式原来普遍需要的检索时间。C→D 只验证实际序列化参数/模型档位；固定夹具不模拟关闭思考对真实供应商的提速。夹具有意在所有配置发送 reasoning 事件以验证计时隔离，即使 D 已关闭思考也一样。

### 题目与来源

- **5,280/5,280** 成功请求的实际 request.question 与最终 SDK 当前 user message，完整匹配 NFKC/空白规范化后的目标；没有额外 SDK 调用。这里核验的是实际回答目标，不是固定夹具答案的内容质量。
- 57 个 QuestionResolver 回归覆盖短停顿新题、纠正、有效 interim、同题多段条件、同 key 修订、乱序、重连、claim/settle、长题与手动 Unicode 原文。完整 Java 编码要求没有问号也可建立目标。
- 新增实际 SDK 回归覆盖 A 生成中提交 B、迟到 token/usage/error/ack 隔离、旧 pending 不进新任务或扩大输出预算、无新题不复活旧题、显式重答保留技术模式、最小指代参考、明确未知项目不继承旧事实。
- ready-only 用会抛错的前台磁盘/词法/父块访问及挂起语义任务验证零调用；标准回退仍可 scoped 检索。超预算来源整块跳过，最终可见命中和 sourceCount 正确。手工卡片不能凭提到另一个项目就跨项目附入。

暖缓存并非万能命中：普通组 C/D 各 120/780 次使用了 ready 来源，CPU 组各 80/540 次；暖缓存场景的每组为 20/30，其他请求按设计继续作答。实测 C/D 来源最多 2 个，低于硬上限 3；最终证据/手工卡片共用 650 本地估算 token 可选预算，用户当前题和风格优先。没有生成模型，故不能测“生成回答正确率”或“幻觉率”；项目事实是否适用于用户真实经历仍须核验。

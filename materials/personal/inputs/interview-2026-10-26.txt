4. **验证方式**：留一部分历史算例做**留出验证**，看代理模型预测误差是否在工程可接受范围；平台侧看**单次仿真准备时间**和人工干预次数的下降。如果改代理模型方案，我会用**物理仿真+AI校正**的混合方式，边界是只用于早期方案筛选，不进入最终签核。

对应问题：呃,那为什么上下文它会有一个那个?
长度的限制,对吧?我们通常说上下文窗口,它可能是 256K 啊,1M 的那种。它为什么会有这么一的上下文
1. **本质是注意力计算和显存的二次成本**：上下文长度每翻一倍，Transformer 自注意力的计算量大致变为四倍，因为每个 token 要和前面所有 token 算相关性。256K 上下文光是注意力矩阵就很重，1M 更是指数级放大，不是想开多大就开多大。

2. **KV Cache 是更硬的瓶颈**：推理时每个 token 的历史都要在显存里存一份 Key/Value，长度线性增长。1M token 乘上几十层、多个头、FP16，单个请求就能吃掉几十 GB 显存，并发一多直接爆。这是 256K、1M 这种窗口上限最直接的原因。

3. **训练和位置编码的边界**：模型训练时就固定了最大长度，位置编码、RoPE 外推在超出训练长度后质量明显下降，硬拉长会“记住了位置但理解不了内容”。长上下文还伴随“中间遗忘”，信息放在中间段召回率差。

4. **工程取舍**：所以现在的做法是长窗口配合 RAG、摘要、分块，把真正相关的片段喂进去，而不是无脑塞满。比如一份几百页的仿真报告，我会先检索命中的工况和参数段落再拼上下文，而不是把整份文件塞进 1M 窗口——省显存、延迟低、召回也更稳。

5. **一句话结论**：上下文窗口的上限是**注意力成本、KV Cache 显存、训练位置编码和效果质量**共同卡的，不是单纯的数字偏好。

[2026/10/26 11:05:05] CUE 建议（未确认说出）
对应问题：哦,那你刚才提到的 Transformer,你可以简单讲一讲 Transformer 的这个机制吗?
1. **核心机制是自注意力**：每个 Token 都生成 Query、Key、Value 三个向量，用 Q 和所有 K 点积算出相关性分数，softmax 归一化后作为权重对 V 加权求和，得到这个位置的上下文表示。这样每个词都能直接“看到”序列里任意其他词，不像 RNN 必须逐步传递。

对应问题：那那这个点为什么一定要用 Workflow 呢?我能不能使用去使用 Skill 这些东西去替代它?
1. **为什么一定要用 Workflow**：核心是**约束“不可跳过的执行顺序”，而不是限制模型单轮里的自由**。Coding agent 里模型可以自主选读哪个文件、跑哪条命令，但“改完必须跑测试、测试失败必须回到修复、通过后必须产出验证记录”这种**外层任务骨架**不能交给模型即兴决定；否则模型容易在同一个文件上打空转，或者把测试直接跳过还宣称完成。Workflow 兜的是**终止条件和必经环节**，ReAct 管的是**单步探索**，两者职责不同。

2. **Skill 能不能替代**：部分能，但替代不了全部。Skill 更适合封装“怎么做某件事”的知识和工具调用，比如“跑集成测试的步骤”“提交前检查清单”；它本质还是挂在模型决策树上的一环，模型可以选择不调用或调用后不跟进。如果只靠 Skill，模型仍有跳过测试、循环空转的自由度。**Skill 是能力供给，Workflow 是流程强制**，前者给“会做”，后者保“一定做”。

3. **如果改用纯 Skill 方案**：我会把关键环节做成**带前置条件和后置校验的 Skill**，比如测试 Skill 返回结构化结果，主循环里用代码判断“没有测试通过记录就不能进入完成态”。这实际上是把一部分 Workflow 逻辑下沉到了执行器和状态机里。边界是：复杂度会上移，校验散落在各 Skill 中，跨步骤的**全局顺序和重试上限**不如显式 Workflow 清晰，适合流程较短的场景。

4. **我的取舍**：外层用 **Workflow 定义阶段和退出条件**，内层单个阶段里放开 **ReAct 自由探索**，可复用能力封装成 Skill 供模型和 Workflow 共同调用。这样既保留单轮自主性，又用固定骨架防止打空转和跳测试。

对应问题：OK,嗯,那你有了解过MCP和除了呃,Function Call还有一个那个Skill吧?他们三个有什么区别?
1. **Function Call 是模型层的基础能力**：模型按约定格式输出一个结构化调用请求，比如 `{"name":"search","arguments":{"q":"..."}}`，由宿主程序真正去执行，再把结果回填给模型。它本身只解决“怎么表达要调什么”，不解决工具从哪来、怎么复用、怎么做权限和发现。

2. **MCP 是工具接入的协议层**：作用是把“工具/资源从哪来、怎么暴露给 Agent”标准化。比如一个本地文件服务用 MCP 暴露 `read_file`、`list_dir`，Claude Code 或其他客户端按协议连上就能发现并调用，不用每个 Agent 各自写一套适配。它管的是**连接、发现、能力描述**，至于模型这一轮要不要调、怎么调，仍走 Function Call 那套。

3. **Skill 是封装好的任务方法/操作说明**：更像给 Agent 的一份“可复用做法包”，包含步骤、约束、脚本或模板，告诉它某类任务该按什么流程做。比如“发布前检查”这个 Skill 里写清跑哪些命令、看哪些文件、什么情况算通过。它解决的是**怎么做对一类事**，不是新增一个原子工具接口。

4. **区别落在层次上**：Function Call 是“调用表达”，MCP 是“工具来源与接入”，Skill 是“任务级方法论与流程封装”。三者可以叠加：Skill 里指定用某个 MCP 提供的工具，执行时最终仍以 Function Call 形式发出。取舍上，单体内几个固定工具用 Function Call 就够；工具要跨客户端复用、要动态发现就上 MCP；流程长、步骤固定、要减少重复推理，就封装成 Skill，这也正好对应 Plan and Execute 那种可预见步骤的场景。

1. **标准 RAG**：先按问题做向量或关键词召回，把 Top-K 片段拼进上下文再生成。关键取舍在**召回粒度**和**重排**——块切太碎丢上下文，切太大引入噪声，所以我会先粗召回再交叉编码器重排，并用带答案的查询集验证召回率，而不是只看相似度分数。

2. **Agentic RAG**：把检索变成 Agent 可调的工具，由模型判断**要不要查、查几轮、换不换查询**。它适合多跳和需要判断证据是否充分的问题；代价是延迟和成本上升，所以我会设最大检索轮数（比如 3~5 轮）、查询去重和“证据已足够”的提前退出条件，避免空转。

3. **GraphRAG**：先抽实体和关系建图，再沿社区或子图做摘要和检索，适合**跨文档的全局性、关系型问题**，比如“这些报告里哪些实体之间存在间接关联”。它的代价是建图和增量更新成本高，抽取错误还会沿图传播，所以我会保留原文指针做溯源，并用问题集对比它和向量 RAG 的答对率来决定是否值得上。

4. 我的选型判断：**单跳事实问答**用标准 RAG 加混合检索和重排；**多跳、需要边查边推理**用 Agentic RAG；**全局归纳和实体关系**用 GraphRAG，必要时与向量检索组成混合路由，按问题类型分流而不是全部混在一起。

1. **核心原因是“要的是当前真相，不是相似片段”**：Coding agent 面对的是刚改过的文件、刚跑出的报错、刚定的接口契约，这些**以工作区实时状态为准**；RAG 返回的是索引时刻的相似片段，容易给出过期代码或错误版本，且无法保证完整语义。我会用**按需读取+精确检索**（grep/glob、读文件、跑测试）替代向量召回，让模型自己决定“读什么、跑什么”。

2. **不做向量库，但仍做检索**：Claude Code、Codex 这类工具用**关键词/正则搜索、目录浏览、按行读取、编译器与测试反馈**来定位代码，本质是确定性、可验证的检索；命中后还能回源看完整文件。向量 RAG 只能给“像”的代码块，缺上下文边界，容易出现拼接幻觉，**验证成本反而更高**。

3. **上下文管理靠压缩和分层，不靠召回**：就像你说的，**必须保留的**是用户约束、未完成目标、失败事实和最近几轮关键输出；**可摘要的**是早期讨论和已解决的中间产物。配合 **max step 8~15 轮**防空转、不可恢复异常直接终止，这比“把历史塞进向量库再捞回来”更可控。

4. **取舍与验证方式**：如果改用 RAG，我会限定在**稳定知识**场景，比如文档、规范、历史 issue，并且**强制回源打开原文件核对**，检索结果只作导航不做答案。验证上会对比同一任务在“全量文件读取+grep”与“RAG 召回”下的**定位准确率、上下文 token 成本、错误回退次数**；当前工程实践里前者在代码库内更稳，所以主流 Coding agent 不走 RAG 路线。

要去怎么融合这些,有有了解过?
1. **Agentic RAG 的融合核心是“先路由、再检索、后重排与压缩”**：我先判断当前问题是需要查知识库、查代码库还是直接回答，再按问题类型分别走**关键词检索**和**向量检索**，把两路召回结果按 `score = α·关键词分 + β·向量分 + γ·时效/权威性权重` 合并去重，最后交给模型生成。比如运维问题里“报错码”偏关键词、经验类描述偏向向量，双路融合比单路稳。

2. **融合时要做“证据选择”而不是全部塞进上下文**：按**相关性、新鲜度、来源权威性、互相支持度**打分截断，冲突证据显式保留并让模型比较，检索结果标明来源和更新时间，避免旧文档压过新接口。若检索结果为空或置信度低，我会让 agent **改写查询再检一次**，仍不行就回退到直接回答并说明依据不足。

3. **如果改用图结构融合**：我会把实体、文件、接口建成**知识图谱或代码依赖图**，先用向量找到入口节点，再沿图扩展相邻节点做证据补全；边界是图维护成本高、更新要跟代码变更同步，适合模块多、依赖复杂的场景，不适合小而频繁变动的零散文档。

对应问题：Rerank 这些有有了解过吗?
1. **Rerank 的作用**：检索先用向量召回或 BM25 拿 Top-K 候选，再用交叉编码器（cross-encoder）对“查询-文档”逐对打分重排，取前 N 条喂给模型。它比双塔召回准，但每条候选都要过一遍模型，延迟和成本随候选数线性涨，所以只精排小窗口，比如召回 50 条重排到 5～10 条。

2. **工程上的取舍**：延迟敏感时用轻量 rerank 模型或只对高不确定候选重排；离线评测看 **Recall@K 和 nDCG**，同时监控 P99 延迟和 token 成本。很多框架（LangChain、LlamaIndex、Cohere Rerank）都支持把 rerank 插在召回和生成之间。

3. **Agent RAG 里的位置**：多轮检索时 rerank 还能结合对话上下文对候选打相关性分，过滤掉过时或指代不明的段落，减少把噪声塞进上下文。

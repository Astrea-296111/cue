## CAE 项目追问

### cae-01 为什么要做 CAE 平台，你负责什么？

这个平台解决的是提交分散、状态难跟踪和结果报告难整理的问题。我负责 Java 后端的任务提交编排、资源约束、可靠性和输入校验，以及结果报告的元数据与阶段重试；求解器数值算法不属于我的工作。

**继续追问：** 为什么原来的脚本不够用？；哪些是你独立实现的？；一条任务链路经过哪些模块？

**边界：** 职责来源为简历声明，不根据代码文件数量推断个人贡献。

**资料属性：** resume_claim；来源 resume, R3

### cae-02 281 ms 到底测的是什么？

这是简历所述配置下批次持久受理的 P95，不是求解完成时间。请求完成必要校验并把批次意图可靠保存后可以返回；后续任务接入、排队、求解和报告分别计时，不能把这几段合成一个数字。

**继续追问：** 计时从哪到哪？；300 个样本怎样取 P95？；为什么要优化受理而不只优化 Solver？

**边界：** 5 并发、每批 50 Case、300 批次属于简历测试声明；不可冒充当前公开基准。

**资料属性：** resume_claim；来源 resume, R3

### cae-03 为什么采用模块化单体而不是微服务？

任务、资源和执行状态的事务关系紧密，先用模块边界把领域分清，比一开始拆很多服务更容易保证一致性和排查问题。远程 Worker 仍通过明确协议解耦。只有独立扩缩容、团队边界或发布节奏确实成为瓶颈时才考虑继续拆分。

**继续追问：** 哪些模块最先拆？；事务怎么跨服务？；单体是否无法扩展？

**边界：** 不要虚构生产集群规模或微服务迁移已完成。

**资料属性：** code_and_design；来源 R3

### cae-04 为什么用 RabbitMQ，不直接 HTTP 或 Kafka？

数据库保存业务状态，RabbitMQ 传输有边界的任务命令，适合解耦受理与耗时执行，并支持重试和失败隔离。直接 HTTP 仍可用于实际 Agent 交互，但前端不能等待 Solver 完成；Kafka 的日志回放和分区顺序也不能替我解决业务幂等。

**继续追问：** HTTP 超时但实际执行了怎么办？；Kafka 什么场景更合适？；队列堆积怎么发现？

**边界：** 实际项目为 RabbitMQ；备选 Kafka 只能作为比较。

**资料属性：** code_and_design；来源 R3, R7

### cae-05 Outbox 为什么能解决保存成功但消息没发出去？

业务变化和待发事件在同一数据库事务落盘，发布器再独立投递。这样进程在事务提交后宕机，待发记录仍能被扫描到。发布成功到标记 SENT 之间还有故障窗口，所以它改善可靠交付，但仍需要消费与执行端幂等。

**继续追问：** 为什么不在事务里一直等 MQ？；confirm 后更新数据库前宕机？；发布器并发怎样领取？

**边界：** 不能把 Outbox 说成消灭重复投递。

**资料属性：** code_and_design；来源 R3, R7

### cae-06 publisher confirm 与 consumer ACK 是一回事吗？

不是同一个边界。confirm 是发布端与 broker 之间的确认，consumer ACK 是消费端对消息处理边界的确认。这里消费者完成可靠业务受理后 ACK，不等求解器跑完；最终执行结果由 Execution 状态和对账链路管理。

**继续追问：** ACK 早了会怎样？；业务提交后 ACK 丢了呢？；积压与处理失败怎样区分？

**边界：** 不声称收到 confirm 就证明业务已完成。

**资料属性：** code_and_design；来源 R3, R7

### cae-07 500 次重放没有新进程，幂等键到底是什么？

要分清请求身份、消息身份和执行身份。相同逻辑请求应命中已有受理结果，消息重投应复用已有业务处理记录；向 Worker 提交还要带稳定的执行身份并核验返回。验证时同时看 Job、Execution 与远端进程，不能只数数据库行。

**继续追问：** 重跑与重试用同一个身份吗？；参数变了但 key 没变呢？；数据库唯一约束起什么作用？

**边界：** 500 次是限定测试声明；具体 key 字段由当前源码核验后落卡。

**资料属性：** resume_claim_and_code；来源 resume, R3

### cae-08 为什么要拆 Job 与 Execution？

Job 表达用户想完成的工作，Execution 表达某次实际执行尝试。把它们分开，重试、取消、远端状态和历史产物就不会混在一条记录里；新尝试也不能被旧尝试迟到的回调覆盖。

**继续追问：** 为什么一个 status 字段不够？；同一 Job 有几个活跃尝试？；终态回调乱序怎么办？

**边界：** 幂等身份与状态转换约束以实现为准，不无条件承诺严格恰好一次。

**资料属性：** code_and_design；来源 R3

### cae-09 Worker 心跳没了，为什么不能马上释放资源？

心跳不可达不能证明求解进程停止。如果先释放 CPU、内存或 License 账本，可能让新任务占到仍在使用的资源。应保留不确定执行身份，主动核验远端进程或权威终态，再让业务状态和资源账本收敛。

**继续追问：** 一直查询失败怎么办？；什么时候人工介入？；租约过期等于进程结束吗？

**边界：** 不要把 PID 校验等同于 fencing；没有证据不补造可靠栅栏。

**资料属性：** code_and_design；来源 R3

### cae-10 CPU、内存和 License 怎么一起预占？

把多维容量当作同一受理条件：任意一项不足就不派发。并发请求必须在受控事务与条件检查下更新持久账本，不能只读一次剩余量再在内存减数；释放也要绑定执行身份并能幂等处理。

**继续追问：** 两台调度器同时抢最后一个 License？；大任务饥饿怎么办？；资源拒绝算系统错误吗？

**边界：** 具体锁和 SQL 需要源码定位；不要默认用了 Redis 分布式锁。

**资料属性：** code_and_design；来源 R3

### cae-11 取消请求和成功回调同时到来怎么办？

取消是一个请求，不代表远端已经停止。应区分取消意图、执行状态与资源释放，按同一 Execution 的允许状态转换处理迟到消息，并重新核验远端事实。终态不能被旧消息随意回滚，释放必须防重复。

**继续追问：** 进程已经退出但回调未到？；重试和取消交错？；前端显示什么？

**边界：** 不承诺取消后瞬间没有任何远端副作用。

**资料属性：** code_and_design；来源 R3

### cae-12 INCLUDE 预检检查什么，为什么还要快照？

预检先解决依赖是否存在、路径是否越界和模型引用是否可解析；快照解决校验后到执行前输入又变化的问题。执行前核对依赖和版本，使一次结果能对应到确定输入，而不只依赖一个可能已经迁移的路径。

**继续追问：** 软链接越界怎么办？；校验后文件被修改？；大量小文件怎么优化？

**边界：** 120 组是有限样本；不能保证解析所有求解器语法。

**资料属性：** resume_claim_and_code；来源 resume, R3

### cae-13 为什么用 NFS，而不是把模型放消息里？

模型和结果体积较大，队列只传任务身份和可定位的输入信息，实际文件通过共享存储交接，减少消息膨胀。代价是要治理路径、权限、可见性和版本，文件存在也不等于完整可用；后续迁对象存储需要改协议和一致性校验。

**继续追问：** 写一半被读到怎么办？；多节点路径不一致？；对象存储会解决全部问题吗？

**边界：** 不能把本地路径假设外推到所有部署。

**资料属性：** code_and_design；来源 R3

### cae-14 报告失败为什么不重新跑仿真？

求解、解析、后处理和报告是不同阶段。如果失败只发生在渲染，应该复用已经确认的上游产物，从对应阶段重试。产物要绑定输入、执行与模板版本，防止新模板或旧结果混在一起，造成看似成功但内容不一致。

**继续追问：** 如何判断能复用哪个阶段？；模板变了如何失效？；重复回调会生成多份报告吗？

**边界：** 不得宣称报告可以替代全部人工审核。

**资料属性：** code_and_design；来源 R3

### cae-15 报告省了 76.3%，这个数怎么比较？

比较对象必须是相同内容与相同审核要求下的人工整理流程和平台辅助流程。记录各配对样本的开始结束与异常情况，说明采用总时长比还是逐样本均值，再给减少比例；它衡量整理效率，不代表求解速度。

**继续追问：** 30 组是否有偏差？；审核时间算没算？；异常样本怎么处理？

**边界：** 简历未给原始样本时不编造实验表；用明示的复现方案回答。

**资料属性：** resume_claim；来源 resume

### cae-16 你如何监控链路，而不只看平均耗时？

把受理、排队、Agent 提交、求解和报告分段看，同时关注 Outbox 积压量和最老消息年龄、节点状态与资源账本。公开实现有 Actuator/Prometheus 和 Grafana；状态快照用 Gauge，事件累加用 Counter，不能对所有名字带 total 的指标直接 rate。

**继续追问：** 怎样配置抓取？；P95 为什么比平均值有用？；为什么 jobId 不做 label？

**边界：** 公开实现的部分 total 名称实际为 Gauge，按真实类型答。

**资料属性：** code_and_design；来源 R3

### cae-17 异步线程和 MQ 中 traceId 会自动传吗？

不能假设线程本地变量会跨线程或跨消息自动传播。日志关联要在提交异步任务时捕获上下文、执行时恢复并在 finally 清理；跨进程则显式传递约定字段。当前代码能证明到哪里就讲哪里，业务 ID 关联日志不等于完整分布式追踪。

**继续追问：** 线程池复用为什么会串号？；跨 MQ 怎么传？；Python Worker 如何关联？

**边界：** 增强方案与当前已实现能力分开，不编造全链路 OpenTelemetry 已接入。

**资料属性：** code_and_proposed_design；来源 R3, R10

### cae-18 怎么设计可靠性测试而不是测正常流程？

在事务提交、publish confirm、消费提交、Agent 受理、终态回调和资源释放这些边界注入中断或重放。每次断言业务状态、执行身份和资源账本最终一致，同时检查有没有新增进程和重复产物。恢复时间从条件满足后计算，保留未收敛样本。

**继续追问：** 网络恢复但进程仍失联？；如何控制故障可复现？；为什么只看 HTTP 200 不够？

**边界：** 测试成功只覆盖已声明的故障模型。

**资料属性：** design_for_validation；来源 resume, R3

### cae-19 知道 Job ID 就能读别人的任务吗？

权限必须在服务端根据已认证身份和任务所属项目检查，不能信任前端传来的用户信息。公开 ProjectAccess 有角色和项目成员检查、Owner/Lead 边界；文件下载和后台回调也需要分别审查，不能因为列表过滤就认为所有入口都安全。

**继续追问：** 管理员如何审计？；跨项目猜 ID？；缓存了权限后撤权怎么办？

**边界：** 项目成员控制不等于完整多租户 RBAC/KMS 中台。

**资料属性：** code_and_design；来源 R3

### cae-20 慢 SQL 如何优化，怎么证明有效？

先从真实慢请求定位 SQL、参数分布、扫描行数和执行计划，再判断联合索引、回表、排序或锁等待问题。对照同一数据量与相同负载测试 P95 和错误率，同时验证写入代价；不能只加索引后测一条热缓存请求就宣布优化成功。

**继续追问：** 索引顺序怎么定？；为什么不用缓存直接解决？；锁等待和 CPU 慢怎样区分？

**边界：** 通用排查方法，不能编造项目已有 800→150 ms 优化。

**资料属性：** general_knowledge；来源 R3

## Arclight 项目追问

### arc-01 Arclight 是什么，你自己实现了什么？

它是把模型、工具、文件编辑和测试串起来的终端 Coding Agent。作为个人项目，我关注运行闭环、上下文预算、MCP/Skills 扩展和多 Agent 协作，而不是训练基础模型；第三方 SDK 与界面库提供基础能力，我实现的是它们之间的控制和状态逻辑。

**继续追问：** 为什么不用现成工具？；哪部分最体现个人工作？；内部 mewcode 是什么？

**边界：** 个人项目来自简历；不要编真人团队或开源贡献。

**资料属性：** resume_claim_and_code；来源 resume, R2

### arc-02 一轮 Agent Loop 具体怎么跑？

模型收到任务和当前工具描述后输出正文或调用意图；运行时解析并校验参数，执行允许的工具，把结构化结果与错误送回下一轮，再决定继续还是结束。完成判定需要看文件变化和测试结果，不能只看模型说 done。

**继续追问：** 非法参数怎么回注？；重复失败怎样停止？；工具返回很大怎么办？

**边界：** 迭代上限和权限边界不能为了演示成功删除。

**资料属性：** code_and_design；来源 R2

### arc-03 为什么不用 LangGraph 或固定 Workflow？

如果流程稳定，固定工作流更易测试。Coding 任务的下一步常依赖代码与报错，动态 Loop 更灵活；自建运行时能细控流式事件、工具预算和会话恢复。代价是要自己承担状态、兼容和评测；LangGraph 的持久化机制可以作为设计比较，不是我已经使用它的证据。

**继续追问：** 什么部分仍适合确定性脚本？；自研的收益怎么测？；后续迁框架成本？

**边界：** 简历技能熟悉 LangGraph 不等于 Arclight 依赖它。

**资料属性：** code_and_design；来源 R2, R11

### arc-04 为什么长会话会变差？

不仅是超过窗口，长日志还会挤占任务约束和关键代码，使下一轮注意力落在低价值内容上。我把大工具结果落盘并保留可定位预览，结合近期原文与较早历史摘要控制输入；需要细节时读回对应片段。

**继续追问：** 为什么不直接截断？；怎样防摘要丢约束？；落盘路径丢了怎么办？

**边界：** 摘要有损，不宣称完全无损记忆。

**资料属性：** code_and_design；来源 R2

### arc-05 上下文压缩怎么保留 tool call 配对？

压缩不能只按字符切断消息序列。要明确保留窗口与摘要边界，维护调用与结果的对应关系，对未完成调用保持可识别的中断状态；恢复时读取持久化边界，避免出现只有结果没有调用或反过来的消息。

**继续追问：** fork 时遇到进行中的调用？；摘要失败怎么办？；压缩前后怎样回放验证？

**边界：** 具体边界对象以 CompactBoundary 与会话实现为准。

**资料属性：** code_and_design；来源 R2

### arc-06 31.57% 的 Token 减少代表什么？

这是简历中 60 项长会话对比的累计输入 Token 指标。比较时需要固定任务、模型和工具条件，同时看完成率是否下降；输入少了不一定总费用同幅下降，因为输出和额外摘要调用也有成本。

**继续追问：** 累计输入怎么算？；失败任务是否计入？；摘要调用 Token 算不算？

**边界：** 没有原始日志不宣称已经复核该数。

**资料属性：** resume_claim；来源 resume, R2

### arc-07 50 个工具为什么不全部塞进去？

全量工具 Schema 会占初始上下文，也增加选择干扰。通过工具搜索先找到相关能力，再加载完整描述与参数 Schema，让模型看到当前需要的工具；工具真正执行前仍做参数与权限校验。

**继续追问：** 找错工具怎么办？；目录变更如何刷新？；18.6k→4.2k 的边界是什么？

**边界：** 初始上下文下降不等于完整任务总 Token 同幅下降。

**资料属性：** resume_claim_and_code；来源 resume, R2, R9

### arc-08 MCP、Tool Calling 和 Skill 有什么区别？

Tool Calling 是模型表达调用意图的方式，MCP 规范外部能力如何被发现和调用，Skill 则组织任务步骤、提示和可复用资源。它们可以组合：Skill 指导流程，模型选择工具，运行时通过 MCP 或本地适配器执行。

**继续追问：** Skill 能否替代权限控制？；怎样做渐进加载？；工具错误在哪里处理？

**边界：** 不要把 Skill 文本本身当执行授权，也不要说 MCP 自动解决业务幂等。

**资料属性：** general_knowledge；来源 R2, R9

### arc-09 Pydantic 已校验参数，还要校验什么？

类型和字段校验只能保证输入形状合理，不能证明路径在授权目录、命令安全或业务状态允许。工具层还需检查语义、资源范围与副作用，失败时返回模型能修正的错误信息，并避免泄露环境秘密。

**继续追问：** 路径穿越如何挡？；错误重试会重复写文件吗？；Schema 与实际参数漂移怎么办？

**边界：** 不把类型校验等同于安全沙箱。

**资料属性：** code_and_design；来源 R2

### arc-10 异步 Agent 为什么也会卡住？

asyncio 的收益主要来自等待期间让出执行权。如果工具里有同步磁盘大操作、CPU 重活或阻塞 subprocess，仍会堵住事件循环。要分清协程并发与真正并行，把阻塞部分隔离，并让超时和取消能传播到子任务。

**继续追问：** gather 一个失败其他怎么处理？；取消会自动终止子进程吗？；如何测 event-loop delay？

**边界：** 通用设计解释，不断言所有工具已经做到完整取消。

**资料属性：** general_knowledge；来源 R2

### arc-11 什么时候拆子 Agent，什么时候不拆？

依赖少、可独立验证的探索任务适合拆分，主代理保留整合和验收。强依赖或频繁互相等待的修改不一定受益，因为拆分有上下文复制和协调成本；不能为了多 Agent 而多 Agent。

**继续追问：** 探索、规划、验证如何分工？；输出如何汇总？；重复探索怎样去重？

**边界：** 软件角色不是现实项目团队人数。

**资料属性：** code_and_design；来源 R2

### arc-12 为什么耗时少 23.1%，Token 却多 32.16%？

并行把独立工作同时做，缩短的是墙钟时间；每个代理都有自己的上下文与推理，重复阅读和协同消息会增加总 Token。所以这个结果体现时间和成本的交换，只能在适合并行的任务上评估。

**继续追问：** 怎么控制并行度？；比较基线一致吗？；什么时候退回单代理？

**边界：** 百分比为简历声明，不能声称所有任务都更快。

**资料属性：** resume_claim；来源 resume, R2

### arc-13 worktree 能保证多个 Agent 不冲突吗？

它让各个工作目录和分支独立，适合隔离文件修改，但不能自动解决合并冲突，也不会隔离共享任务文件、外部数据库或端口。需要约定文件归属，整合时检查 diff、跑相关测试，再处理冲突。

**继续追问：** 同一文件被两人改？；依赖安装和端口冲突？；什么时候不用 worktree？

**边界：** 不把 worktree 说成系统级沙箱。

**资料属性：** code_and_design；来源 R2

### arc-14 SharedTaskStore 已经有跨进程 CAS 吗？

当前可见实现是文件持久化，不能据此声称已有跨进程 CAS 或强一致事务。多写者会有覆盖和丢更新风险；要增强，需要选定单写者、锁或事务存储等策略，并用真实并发和中断测试验证。

**继续追问：** 原子 rename 能解决丢更新吗？；改 SQLite 有什么收益？；锁持有者宕机怎么办？

**边界：** 原子写文件只解决部分可见性问题，不自动解决读改写竞争。

**资料属性：** code_and_design；来源 R2

### arc-15 Mailbox consume 是事务 ACK 吗？

当前 Mailbox 是文件消息机制，读取、处理、删除之间不构成完整事务 ACK，不能保证处理副作用与删除原子一致。若要提高可靠性，可以引入领取、处理中、确认与重投协议，再配合幂等处理；这是改进方案。

**继续追问：** 读后进程崩溃？；删除失败？；重复消息如何识别？

**边界：** 明确当前实现边界，不把拟议协议说成已实现。

**资料属性：** code_and_design；来源 R2

### arc-16 JSONL 恢复是不是重新执行所有工具？

会话恢复首先是重建已保存的上下文和状态，不应把历史工具副作用无条件重放。对已完成、未完成和结果缺失的调用需要分别处理，尤其是文件写入和命令执行；恢复后还要核验文件与记录是否一致。

**继续追问：** 最后一行写一半怎么办？；当前工作目录变了？；工具结果文件丢失？

**边界：** 持久化历史不等于任意外部副作用都可以回滚。

**资料属性：** code_and_design；来源 R2

### arc-17 长期记忆和会话压缩是什么关系？

压缩是当前会话预算管理，长期记忆是跨会话保存仍有价值的信息。长期记忆应带来源、更新时间与适用范围，项目代码变化后可能失效；不能把模型一次错误总结固化成永久事实。

**继续追问：** 哪些东西不该记？；过期怎么判断？；如何避免跨项目串记忆？

**边界：** 不把摘要等同于知识库事实。

**资料属性：** code_and_design；来源 R2, R11

### arc-18 SWE-bench 怎么判修好了？

给定仓库、问题和基准版本，让 Agent 产生补丁，再在隔离环境应用补丁并执行对应测试，检查问题修复和原有行为回归。比较不同 Agent 时固定模型、样本、预算及环境，失败和环境错误都需要单独记录。

**继续追问：** 为什么不用模型自评？；FAIL_TO_PASS 和 PASS_TO_PASS？；官方 harness 与自写脚本差别？

**边界：** 简历 300 题结果为声明，不补造逐题日志或官方榜单记录。；31.33%到43.67%展示值相减为12.34个百分点；按约94到131个成功还原为12.33个百分点，是舍入差异。

**资料属性：** resume_claim_and_method；来源 resume, R2, R8

### arc-19 解决率提升能证明全是多 Agent 的功劳吗？

不能。多个组件同时变化无法归因，需要在同模型、同题集和可比预算下分别关闭上下文管理、工具发现或协作，观察成功率、耗时和 Token。还要看失败类型与重复运行波动，不能只报一个汇总百分比。

**继续追问：** 随机性怎么控制？；相同预算怎么定义？；是否过拟合公开题？

**边界：** 不要把不同模型或预算的差异算成框架提升。

**资料属性：** evaluation_method；来源 resume, R8

### arc-20 Arclight 最大的下一步改进是什么？

我会优先补可靠协作与可复现评测：把文件状态的并发边界讲清并加故障测试，把不同组件的收益用统一任务和成本口径验证。只有这些基础可靠，增加更多 Agent 或复杂记忆才有意义。

**继续追问：** 先改哪个模块？；风险怎么控制？；如何判断重构值得？

**边界：** 这是改进优先级，不是已完成结果。

**资料属性：** proposed_design；来源 R2

## 工程通用问题与岗位衔接

### gen-01 项目中最难的一件事怎么讲？

选择一件有明确失败现象的事情，说明它破坏了哪个业务约束、如何缩小范围、排除过什么方案、最后改了哪个边界，再讲验证和剩余限制。不要用“用了分布式锁所以很难”代替实际问题。

**继续追问：** 第一次判断错在哪？；什么证据推翻了假设？；重做会怎么简化？

**边界：** 可结合附件故事，但不能虚构实际测试已经执行。

**资料属性：** answer_framework；来源 R1, R4

### gen-02 怎么回答你和团队分别做了什么？

把需求与整体协同、自己设计实现的模块、他人提供的输入和共同验收分开。CAE 可以说后端与后处理联调边界，Arclight 按个人项目讲；无法确认的组织人数不随口补。

**继续追问：** 谁定方案？；你做了哪些技术决策？；失败谁负责？

**边界：** 合成协作场景使用角色不使用虚构人名和公司事件。

**资料属性：** answer_framework；来源 resume

### gen-03 你这个项目怎么迭代的？

按问题驱动讲能力阶段：先打通最小链路，再补异常与恢复，再做观测和评测。每阶段都说明上一个版本为什么不够、改了什么、如何兼容旧数据；只有查得到的 commit 或 tag 才说具体版本。

**继续追问：** 如何灰度？；数据迁移失败？；为什么不一次做完整？

**边界：** 叙事阶段不自动等于真实发布 tag。

**资料属性：** answer_framework；来源 R1, R2, R3

### gen-04 测试数据怎么来，怎样避免自测自嗨？

把真实输入格式、边界样本、历史失败、合成故障和留出任务分开建集，保留来源和生成规则。测试数据不能只覆盖自己刚实现的正常路径；失败样本加入回归，同时留出未用于调优的机制家族。

**继续追问：** 合成数据有什么偏差？；数据泄漏怎么防？；如何切片看效果？

**边界：** 不声称合成样本代表完整线上分布。

**资料属性：** evaluation_method；来源 R3, R8

### gen-05 你用 AI Coding 的完整流程是什么？

我先明确输入输出和验收，再让工具读相关模块、提出小范围改动；实现后看 diff、执行相关测试和真实场景，失败时把输入、日志与实际输出交回分析。涉及状态和权限的边界由我核验，模型说通过不能代替退出码与报告。

**继续追问：** 怎么写好任务提示？；上下文放什么？；什么情况自己动手？

**边界：** 不虚构具体未提供的工具使用时长或生产收益。

**资料属性：** answer_framework；来源 R1

### gen-06 AI 写的代码能跑但质量差怎么办？

先用失败用例和调用链确定问题，再要求局部修复并解释不变量。review 要看状态是否重复、异常是否吞掉、资源是否释放、取消能否传播以及测试是否绕开生产路径；功能能跑只是起点。

**继续追问：** 模型一直改坏其他功能？；如何避免测试也被改松？；如何控制补丁大小？

**边界：** 不能以 AI 自动生成测试当作独立证明。

**资料属性：** general_knowledge；来源 R1

### gen-07 项目参考哪些开源，哪些自己写？

先列直接依赖与实际调用，再列确认过的代码复用和设计参考。以 Arclight 为例，模型 SDK、Textual、Pydantic 和 MCP SDK 提供底层能力，运行闭环与预算状态逻辑属于项目编排。相似设计不能证明复制来源。

**继续追问：** 许可证怎么处理？；升级依赖怎么测？；为什么不直接 fork？

**边界：** 不编造 PR、作者联系或历史参考链。

**资料属性：** code_and_design；来源 R2, R9, R12

### gen-08 遇到线上问题你先做什么？

先确认影响范围和可逆止损方式，再结合版本、请求和资源时间线定位最近变化。用最小复现验证假设，修复后回放同类负载并持续观察；给协作方同步事实和下一步，而不是没有依据地猜恢复时间。

**继续追问：** 回滚失败怎么办？；日志不够怎么办？；怎样避免再发生？

**边界：** 通用情境答案，不声称某次线上事故真实发生。

**资料属性：** general_knowledge；来源 R3

### gen-09 为什么不能所有慢问题都加缓存？

缓存会引入过期、失效、并发击穿与数据一致性问题。如果慢在锁竞争、排队或外部执行，加缓存可能掩盖根因。先明确数据新鲜度与允许延迟，选择能接受陈旧的读路径，再测命中、失效和回源峰值。

**继续追问：** 权限缓存能多久失效？；热点 key 失效？；更新与失效竞争？

**边界：** 权限撤销不能仅为低延迟无限期使用旧缓存。

**资料属性：** general_knowledge；来源 R3

### gen-10 如果前面把技术名或指标说错了怎么接？

先用一句话修正具体边界，例如“我刚才说的是受理耗时，不是求解耗时”，再直接回答当前追问。不要用一串新细节掩盖错误；如果只是近似表达，补精确口径即可，不需要每次道歉。

**继续追问：** 已经纠正过还要提醒吗？；对方基于错前提深挖？；ASR 可能听错呢？

**边界：** 实际发言、ASR 文本与项目事实分开。

**资料属性：** answer_framework；来源 R1

### ai-01 Coding Agent 经验怎么迁移到供应链 AI？

可迁移的是工具契约、上下文与状态、可追踪执行及评测闭环。供应链要先定义订单、库存、仓和运输等对象、权限与业务规则，再让模型在限定工具和已发布 Schema 上操作；不能把写代码成功率直接当业务收益。

**继续追问：** 如何定义业务指标？；错误动作如何回退？；哪些环节不交给模型？

**边界：** 这是岗位设计迁移，不是已经做过供应链系统。

**资料属性：** proposed_design；来源 R2

### ai-02 自然语言取数怎样避免乱写 SQL？

先做实体别名与时间口径归一，限定可访问的对象和字段，再进行 Schema Linking 与 SQL 生成。执行前做语法、权限、只读范围和资源预算检查，结果用合计、主外键关系或抽样查询核对；歧义问题要明确假设。

**继续追问：** 跨域补数怎么做？；同名字段如何区分？；SQL 执行成功就算正确吗？

**边界：** 不能称已实现企业数仓或图谱系统。

**资料属性：** proposed_design；来源 jd

### ai-03 什么情况下用混合检索和 Rerank？

业务缩写、代码符号和精确 ID 更依赖关键词，表达改写更适合语义召回，可以合并候选后在预算允许时重排。评估需要区分召回是否找到证据、回答是否正确引用；实时场景要同时测重排增加的延迟。

**继续追问：** 召回率高但答案错？；chunk 怎么切？；为什么不是所有请求都 rerank？

**边界：** 这是简历技能与通用方案，不把 CUE 检索机制说成 Arclight 已有实现。

**资料属性：** general_knowledge；来源 resume, R1

### ai-04 SFT、DPO、RL 与 Prompt 优化怎么区分？

Prompt 和上下文工程主要改变推理时输入；SFT 用示范数据更新参数，DPO 用偏好对进行优化，RL 通过奖励反馈优化策略。先用固定评测确认问题是知识、表达还是决策，再决定是否值得训练；我不会把应用编排说成后训练实操。

**继续追问：** 怎样构建偏好对？；Agent RL 奖励怎么设计？；如何避免只学会迎合裁判？

**边界：** 当前资料未证明实际完成模型后训练。

**资料属性：** general_knowledge；来源 jd

### ai-05 UI 自动化 Agent 怎么评测？

把视觉定位、状态理解、动作执行和最终业务结果拆开看，增加分辨率变化、遮挡、弹窗和页面延迟等切片。操作前后保留可复核状态，危险动作设明确边界；只看模型描述截图正确不能证明点击成功。

**继续追问：** 元素位置变了？；误点后怎么办？；成功标准怎么定义？

**边界：** 不宣称简历项目已有多模态生产部署。

**资料属性：** proposed_design；来源 jd, R5

### ai-06 离线评分更高为什么业务可能没提升？

离线集分布、评分偏好和真实业务流程可能不一致。应把任务成功与业务结果分别定义，按用户类型、长尾与失败成本切片，分析线上反馈再更新评测；不能用语言更流畅替代正确完成业务。

**继续追问：** 用户反馈噪声怎么处理？；如何避免只收好评？；如何控制上线风险？

**边界：** 不编造线上 A/B 实验已完成。

**资料属性：** evaluation_method；来源 R5

### sec-01 如何从 CAE 权限扩展为权限中台？

先明确主体、角色、资源、动作与租户作用域，把策略决策和业务调用分离。CAE 现有角色和项目成员检查能作为起点，但扩展中台还需要策略版本、审计、继承冲突、缓存失效与不同语言 SDK 的一致契约。

**继续追问：** 角色爆炸怎么办？；资源继承怎么处理？；默认允许还是默认拒绝？

**边界：** 不把简单项目鉴权说成成熟权限中台。

**资料属性：** proposed_design；来源 R3, jd

### sec-02 tenantId 由前端传过来就可以了吗？

不能只信前端声明。租户范围应从已验证身份和授权上下文推导，再落实到查询、缓存 key、文件路径和后台任务。测试不仅检查正常租户内访问，还要修改 ID、复用缓存和跨租户猜测资源。

**继续追问：** 管理员跨租户怎么审计？；异步任务丢 tenantId？；缓存 key 漏租户？

**边界：** 是设计要求，不声称 CAE 已实现完整多租户隔离。

**资料属性：** proposed_design；来源 jd, R3

### sec-03 信封加密怎么工作？

大数据通常用数据密钥加密，再由 KMS 管理的密钥保护数据密钥。保存密文和加密后的数据密钥，解密时先获得允许使用的数据密钥，使用后尽快清理明文。还要校验调用身份、用途与审计，不能把密钥写进日志。

**继续追问：** 为什么不让 KMS 加密所有大文件？；密钥轮换后旧数据？；密钥版本如何选择？

**边界：** 属于岗位知识；不声称已有 KMS 项目经历。

**资料属性：** general_knowledge；来源 R16

### sec-04 密钥轮换等于马上把所有数据重加密吗？

要区分保护数据密钥的主密钥版本、数据密钥轮换和全量业务数据重加密。设计时保留密文关联的 key/version 信息，明确旧数据解密与迁移策略；销毁密钥前要评估不可恢复影响与依赖。

**继续追问：** 归档与禁用有什么区别？；回滚怎么办？；谁能批准销毁？

**边界：** 不假设所有 KMS 厂商轮换语义相同。

**资料属性：** general_knowledge；来源 R16, jd

### sec-05 鉴权 SDK 如何兼顾低延迟和撤权及时？

可用本地策略快照或缓存减少远程请求，但要设计版本、失效通知、最大陈旧时间与失败行为。测的不只是热缓存 P95，还包括撤权传播、冷启动、控制面故障和跨租户 key；不能为了可用性默认长期放行。

**继续追问：** 网络断开如何决策？；策略推送漏了？；Java Go Python 如何一致？

**边界：** 此为场景设计，具体 fail-open/closed 由业务风险定义。

**资料属性：** proposed_design；来源 jd

### sec-06 线程池为什么不能无限加线程？

线程数应根据 CPU 和 I/O 等待、下游容量与任务排队共同决定。过多线程会增加切换、内存和连接争用；需要有界队列、明确拒绝策略和指标，避免把压力藏在无限队列中。

**继续追问：** 核心线程数怎么估？；队列满了怎么办？；上下文如何在线程池传播？

**边界：** 不给脱离实际负载的万能线程数。

**资料属性：** general_knowledge；来源 resume

### sec-07 服务响应慢但 CPU 不高怎么查？

先看等待发生在哪里：线程栈、连接池、锁、外部 RPC、磁盘和 GC 暂停，再与时间窗口内请求排队和依赖指标关联。CPU 低只说明没持续计算，不说明系统没有瓶颈；验证单一假设后再调参数。

**继续追问：** 线程都 WAITING 是不是正常？；数据库连接池耗尽？；如何区分 GC 与网络？

**边界：** 不虚构当前项目线上发生过此事故。

**资料属性：** general_knowledge；来源 resume

### sec-08 Redis 锁能替代数据库唯一约束吗？

通常不能。锁是一种并发协调手段，超时、进程故障或租约丢失都可能让调用重叠；业务唯一性仍应由持久化约束和事务处理兜底。拿到锁也不证明远端副作用只发生一次。

**继续追问：** 锁续期失败？；先查再插为什么有竞态？；事务回滚后消息怎么办？

**边界：** 不要凭空给项目加上 Redis 锁实现。

**资料属性：** general_knowledge；来源 R3

## 场景叙事补充

### story-cae-01 确认丢失后的重复提交

**背景：** 用户通过统一入口批量提交仿真任务，界面等待超时后重试。

**触发问题：** 请求返回失败，但 Worker 实际已经受理。

**排查：** 按业务请求、消息和执行身份串起日志，区分没发送、没收到确认和已执行未回写。

**比较过的方案：** 只延长 HTTP 超时不能消除确认丢失；仅查 Job 行也无法判断远端是否重复启动。

**解决路径：** 将稳定身份贯穿受理、投递和远端核验，Outbox 解决待发意图持久化，幂等与对账处理重复和未知。

**验证方案：** 在 Agent 接收后阻断响应，同身份重放；核对 Job/Execution 数量、远端进程与资源账本，再恢复网络。

**取舍与边界：** 可靠性增加了身份和状态复杂度，仍依赖清晰故障模型。

**第一人称场景示例：** 我最先碰到的不是队列吞吐，而是提交超时后任务到底有没有被受理。我的排查从执行身份入手，发现超时不能直接等于失败，所以把重投和新尝试分开，并让对账核验远端事实。

### story-cae-02 License 释放与未知执行

**背景：** 多个小组共享计算和 License 资源。

**触发问题：** 节点失联后如果按超时立即释放，会出现账本可用而远端仍运行。

**排查：** 复核心跳、提交响应、进程状态与资源占用的时间线，发现可达性和执行终态不是同一件事。

**比较过的方案：** 单纯增大租约只推迟问题；在 Redis 中改数字不能证明进程已退出。

**解决路径：** 保留 UNKNOWN 与执行身份，等待主动查询或权威终态后释放；人工处理作为不可恢复分支。

**验证方案：** 模拟短断网、恢复后仍运行、进程已退出但回调丢失三种情形，验证无过早释放和无重复释放。

**取舍与边界：** 宁可短暂降低利用率，也不冒险重复占用；须控制永久挂起的处置。

**第一人称场景示例：** 这个难点是安全与利用率的取舍。节点看不见时我不能假设求解已经结束，因此把未知状态显式留下来，再通过对账决定何时释放资源。

### story-cae-03 目录迁移造成依赖断裂

**背景：** 模型包含多个 INCLUDE 文件，资料目录有调整。

**触发问题：** 主文件存在，任务运行后才发现相对路径依赖缺失。

**排查：** 从失败输入还原依赖图，检查相对路径、越界路径、软链接和校验后修改。

**比较过的方案：** 只检查主文件存在不能覆盖依赖；只修改 UI 提示不能防执行前变化。

**解决路径：** 入口增加依赖预检与路径约束，保存输入快照，执行前核对版本。

**验证方案：** 用缺失依赖、路径越界、目录迁移、执行前篡改和正常输入构成固定样本；计误拦与漏拦。

**取舍与边界：** 预检增加准备耗时和存储开销，解析覆盖面必须写清。

**第一人称场景示例：** 我把错误尽量前移到执行之前：先确认依赖和路径，再固定一次任务使用的输入版本。这样遇到失败时，能够复现当时真正执行的内容。

### story-cae-04 报告模板变更后的阶段重试

**背景：** 仿真结果已生成，业务需要同一结果的标准报告。

**触发问题：** 报告渲染失败或模板变更，直接全流程重跑代价高。

**排查：** 检查失败是解析、后处理还是模板渲染，同时核对上游产物和模板版本。

**比较过的方案：** 全 Job 重跑浪费求解资源；只看文件名复用可能错配版本。

**解决路径：** 分阶段记录产物与状态，以输入和版本指纹决定能否复用，只重试失败阶段。

**验证方案：** 对重复请求、模板更新、迟到回调和已有报告场景验收，检查内容与元数据一致。

**取舍与边界：** 状态与产物关系更复杂，需要清晰失效规则。

**第一人称场景示例：** 我把求解成功和报告成功拆开处理，报告失败时不重新消耗求解资源。关键不是简单加重试，而是证明复用的结果仍与当前模板和输入对应。

### story-cae-05 受理速度与后台积压

**背景：** 批量提交体验需要快速反馈。

**触发问题：** 接口看起来很快，但后面的子任务长时间排队。

**排查：** 分开测批次受理、子任务接入、资源等待与真正执行，检查积压年龄而不只看接口均值。

**比较过的方案：** 单纯增加消费并发可能压垮数据库或资源池；把受理指标当端到端掩盖问题。

**解决路径：** 给受理和执行独立状态，结合背压与资源约束派发，并提供队列与最老任务监控。

**验证方案：** 固定输入规模和资源配额，逐步增加负载；同时看排队、拒绝、完成率与 P95。

**取舍与边界：** 快速受理不消除执行瓶颈，界面要让用户理解当前阶段。

**第一人称场景示例：** 我后来把“提交快”与“任务完成快”分成两件事，不再只看一个接口数值。先明确各阶段耗时，再判断瓶颈在数据库、队列还是资源。

### story-cae-06 后端与后处理接口联调

**背景：** Java 管业务状态，Python 负责部分后处理和渲染。

**触发问题：** 同名字段或版本理解不同，导致状态成功但产物不匹配。

**排查：** 用最小样例逐项核对 Execution、输入摘要、模板版本、错误码及重试语义。

**比较过的方案：** 靠口头约定或宽松 JSON 兼容会把协议错误拖到运行后。

**解决路径：** 固定契约样例和校验规则，联调时先校验输入输出再接入完整批次。

**验证方案：** 对缺字段、类型错、版本错、重复回调和超时分别构造契约测试。

**取舍与边界：** 契约严格会增加协调成本，但能让错误及早暴露。

**第一人称场景示例：** 我的职责主要在后端编排，后处理部分需要联调。遇到理解不一致时，我会用可运行样例和字段契约对齐，而不是在两边各写一层猜测兼容。

### story-arc-01 日志挤掉任务约束

**背景：** Agent 多轮检索和测试产生大量输出。

**触发问题：** 后续回答重复读取文件，甚至忘记最初不能修改的范围。

**排查：** 检查实际发送的 Prompt，区分模型能力问题与关键约束被日志挤掉。

**比较过的方案：** 简单从头截断会删除任务；每轮全部摘要会增加延迟且可能丢细节。

**解决路径：** 大结果落盘，保留定位预览；近期消息保真，较早历史分层压缩，重要约束单独保留。

**验证方案：** 固定长会话任务，对比任务成功、约束保持和累计输入 Token；检查压缩边界前后。

**取舍与边界：** 节省上下文要付出读回和摘要成本，不能承诺无损。

**第一人称场景示例：** 我排查时先看真正发送了什么，发现任务约束被低价值输出挤掉。后来把输出存储与模型可见上下文分开，既控制输入，也能在需要时读回。

### story-arc-02 fork 后工具消息不完整

**背景：** 主 Agent 执行工具时启动子 Agent。

**触发问题：** 新上下文保留了一半工具对话，导致模型协议错误或理解错位。

**排查：** 逐条对比 fork 前的消息、tool_call_id、结果和会话持久化内容。

**比较过的方案：** 按文本长度裁剪无法保证协议结构；直接删除所有历史又丢掉必要任务信息。

**解决路径：** 在边界处理未完成调用，保留完整配对或明确中断标记，再建立子任务上下文。

**验证方案：** 分别在调用前、调用中、结果到达后 fork，验证结构和恢复；失败时检查原始事件。

**取舍与边界：** 上下文继承需要结构规则，不能只用通用字符串裁剪。

**第一人称场景示例：** 这个问题让我把上下文当结构化状态看，而不是一长段文本。fork 时我先保证工具调用关系完整，再决定哪些内容给子代理。

### story-arc-03 工具多但首轮无效上下文过大

**背景：** 配置外部 MCP 服务后可用工具增加。

**触发问题：** 首轮请求包含大量本任务不会用到的 Schema。

**排查：** 统计初始 Prompt 组成、实际使用工具和工具发现失败案例。

**比较过的方案：** 一口气删工具会损失能力；只缩短工具描述可能影响参数理解。

**解决路径：** 用工具目录与 ToolSearch 按需提供完整 Schema，并对目录更新和找不到工具有回退。

**验证方案：** 同任务对照全量与按需策略，统计初始与累计 Token、工具选对率和完成率。

**取舍与边界：** 按需发现会额外占一轮或增加查找成本，要测完整任务。

**第一人称场景示例：** 我优化的不是工具数量本身，而是每次请求看到的工具信息。把发现和调用拆开后，既减少初始负担，也保留了完整参数约束。

### story-arc-04 并行探索与成本上升

**背景：** 多个模块需要相互独立的代码理解。

**触发问题：** 并行更快，但重复读代码与协同消息明显增多。

**排查：** 分别统计每个代理的任务、上下文、墙钟耗时与总 Token，定位重复工作。

**比较过的方案：** 无限增加代理会增加协调和上下文成本；让所有代理修改同一目录会冲突。

**解决路径：** 只拆独立探索，明确输出契约与文件归属，主代理整合并验收；强依赖任务串行。

**验证方案：** 对相同任务做单代理与多代理重复对照，计失败与整合时间。

**取舍与边界：** 接受一定 Token 增长换取时间，必要时退回单代理。

**第一人称场景示例：** 我没有把多 Agent 当作一定省成本的优化。对独立探索它更快，但整体 Token 会增加，所以要让拆分服务于任务依赖关系。

### story-arc-05 文件协作状态的可靠性边界

**背景：** 任务状态和消息通过文件持久化。

**触发问题：** 并发写者或中断可能带来丢更新、部分文件和未确认副作用。

**排查：** 审查 read-modify-write 与 consume 路径，分辨原子写、并发互斥和处理确认。

**比较过的方案：** 不能靠“有文件保存”声称强一致；原子 rename 不解决多个读改写者覆盖。

**解决路径：** 当前回答明确能力边界；后续方案比较单写者、进程锁或事务存储，并设计幂等消费。

**验证方案：** 用多进程竞争和读后崩溃检验提议；没有实现和结果前不宣称修复。

**取舍与边界：** 更强一致性会增加运行时与迁移复杂度。

**第一人称场景示例：** 我会明确区分目前文件机制做到了什么和没有做到什么。要支持更强并发，必须补真正的协议和测试，不能只把名字改成事务。

### story-arc-06 模型说完成但测试未通过

**背景：** Agent 能生成补丁和解释。

**触发问题：** 只看总结很容易把未执行或失败的测试当成修复成功。

**排查：** 对照工具退出码、测试报告、diff 和实际基准版本，发现叙述与执行证据不一致。

**比较过的方案：** 另一个模型觉得代码看起来对不等于可运行，也不能只检查补丁非空。

**解决路径：** 以外部测试 harness 判定任务结果，模型裁判用于补充分类和解释，不替代执行。

**验证方案：** 在固定样本上比较基线与消融，完整保留失败、环境错误和预算。

**取舍与边界：** 可复现评测成本高，但能发现提示词看不出的工程问题。

**第一人称场景示例：** 我最看重的是把“模型说做完了”和“任务实际完成”分开。最终判断来自补丁和测试，不来自它的总结有多像真的。

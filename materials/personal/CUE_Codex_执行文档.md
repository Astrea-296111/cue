## 2. P0：统一口述契约

### 2.1 所有普通问答共用一个策略

建议新建 `src/oral-answer-policy.js`，由标准与极速、手动输入与“如何回答”共同使用。不要留下彼此矛盾的“短答/复杂题不限长”字符串。

| 类型 | 正文目标 | 点数 | 每点 |
|---|---|---|---|
| 简单概念、直接追问 | 80–160 字符 | 2；能一句答清时允许 1 | 2–6 字提示词，紧跟 1–2 句 |
| 项目机制、为什么这样做 | 140–220 字符，硬门槛 ≤260 | 2–3 | 先答结论；至少一处具体动作或小例子 |
| 用户明确要求详细展开/列多项比较 | 240–360 字符 | 3–4 | 仍用短句；不要因出现“设计”自动触发 |
| 写代码、SQL、完整程序 | 解释部分遵守短答；代码独立预算 | 按题意 | 不截断代码，不套口述字数门槛 |

字符统计用可见正文的 Unicode 字符数；去空白和 Markdown 控制符，保留标点、数字、英文。不能用 JS UTF-16 length 当严格字形长度，也不能把 token=中文字符。输出预算先用普通口述约 450–600 token 作保护，经过两家模型实测校准；显式长答单独预算。保持模型 token 上限与可见字符上限两个字段。

默认提示文本：

> 只回答当前问题。默认 2–3 点，每点开头是“做法、原因、例子、结果、边界”等一个短提示词，再跟 1–2 句能直接说出口的话。先给答案，不复述问题，不加“我会从以下几个方面”。普通回答总长不超过260字符。一个概念尽量一直用同一个名称，不为避免重复换同义词。遇到抽象名词，直接跟一个简单例子；不额外开一段术语解释。不重复已回答的项目背景，不自动补总结和下一问。项目事实按来源使用；问没有历史结果的细节时直接给具体做法，不能编结果，也不能把未知说成从未做过。

**流式策略：**首句尽早显示；只做本地段落/句子计数，不默认再调用一个 LLM 改写。超长时保留完整原始输出在 trace，口述卡优先显示完整句，明确 `displayTruncated`。达到供应商 token 上限的 `finish_reason=length` 仍记截断失败，不能靠 UI 切短变成达标。若本地硬门槛截句导致漏关键条件，同样判失败。目标是模型自然给出短答案。

“展开”只在用户点击时追加细节，不自动先生成长答案再藏起来。改口纠正保留一句即可；无关问题不机械加“边界/验证”凑三点。

### 2.2 口述示例

**问：两路召回怎么融合？**

1. 做法：我会先用 RRF，把两路结果按排名合起来，不直接相加原始分数。
2. 例子：同一篇文档在关键词结果排第2、向量结果排第3，两边都会给它加分。
3. 后续：合并去重后，再按需要重排，挑出最相关的几段给模型。

**问：Arclight 的结构化消息长什么样？**

1. 内容：消息里有发送方、接收方、正文和类型，比如探索代理把找到的文件位置发给主代理。
2. 传递：这个版本的 Mailbox 把消息写成 JSON 文件，接收方读取后删除。它适合轻量协作，但不是 RabbitMQ，也没有事务确认。

**问：跑过 benchmark 吗？**

1. 数据：简历里这组是 SWE-bench Lite 的300道修复题，同一 Qwen 模型下比较不同框架配置。
2. 判定：既看原本失败的测试修好没有，也看原来通过的测试有没有被改坏。
3. 结果：简历记录的解决率从31.33%到43.67%，约提高12.34个百分点；60项长会话测的是另一个 Token 指标。

现有 `--publish-readable` 只能作为临时选项，不能视为完整实现：它仍依赖加密输入；工作流的可读输出默认关闭，且公开 Artifacts 不等于无需登录、长期可读的仓库文件。可靠交付是小型正文直接提交到公开结果路径，大文件用公开 Release 并提供索引。发布前用匿名读取核对一个问题、一条答案、一份裁判结果及 workspace，不能只验证自己登录后可下载。

输入 JSON 仅作为数据，禁止执行输入中的代码、shell、路径命令；工作流只在可信 main 或受控已审阅提交使用 Secrets，不能给任意 fork PR 的脚本凭据。无需因此隐藏问题或技术细节。

凭据过滤按明确字段/已知凭据值处理，禁止宽泛数字正则把手机号样式的 case ID、时间戳、指标、测试输入删掉；普通姓名、简历数字、项目和问答按用户要求原样保存。原文到发布文本做差异报告，唯一允许的自动删除是实际认证凭据。不将 `privateOnly` 和 `.cue-private` 当新成品默认发布边界；同步修改编译器、导出器及文档里的过时说明。

中断保存逐条 JSONL/JSON，并保留已完成原始答案；恢复只补未完成条目/裁判，不重复生成来筛选更漂亮答案。400/429/超时、无效JSON、回答错误分别统计。历史解密密钥已丢失的记录明确 unavailable，不编补原回答。

## 6. P1：项目故事与九项实验

按 `docs/Arclight_项目事实与实验.md` 和 `docs/CAE_项目事实与实验.md` 编译；稳定 cardId、字段与来源分开。每个故事都有起因、排查、排除方案、具体动作、验证、剩余问题；主答只取当前需要的两三点，追问才展开。

简历既有数字保留为 USER/source-claim；本包新增实验组、输入样本分配和执行顺序属于 proposed_design；新增场景属于 narrative_scenario。源码证据说明当前实现，不能证明历史团队人数、曾发生事故或测试已执行。不要反复把“模拟/未验证”放进口述每一点；在资料元数据、参考面板及报告中清楚说明，口述用“举个例子/我会这样测”即可。

对已存在的错误卡按同 ID 修订或显式删除/替换，输出迁移差异；不要只增加更多新卡掩盖旧卡。知识集合 general 不计入两项目序号。新文件继续兼容当前 v2；如扩展 schema，提供升级与回退。

不要要求用户提供缺失场景，不生成假的 benchmark CSV。不必为了给 CUE 验收而把 Arclight 的 SWE 300 和 CAE 全实验都真的重跑：**测试 CUE 的回答**与**重做候选人项目实验**是两个任务。本次真实调用重点是 CUE，项目实验给可复现设计；若另行执行，独立报告实际结果。

## 7. P1：速度与检索预算

1. 继续使用已就绪的源码和内存事实；文件解析、索引、故事拆分在导入与后台完成。主问答不串行调用分类、改写、规划、答案润色四个模型。
2. 项目短答选 1–3 张相关事实，源码追问再加 1–2 个关键片段；以实际最终请求检查，不能为省 token 删去单位、条件和否定词。
3. 八股默认不等待项目向量模型。可直接用模型通识和少量同话题历史；不是要求每个问题联网。涉及当前产品版本的断言通过可更新参考资料管理。
4. 用同模型、同材料、同问题比代码；再用同新代码比旧/新材料。否则无法知道收益来自哪边。热缓存与冷启动分开。

工程目标（验收目标，非本次实测）：热准备 P95≤100ms；触发到首个有效语义句 P95≤2.5s；普通完整短答 P95≤6s；>8s 比例≤1%。按供应商分别报告 P50/P95/最大值、样本数、失败和缓存状态。若供应商波动导致未达标，保留真实失败并说明瓶颈，不调统计口径掩盖。来源图标、编号、“正在思考”、reasoning token 均不算首个有效句。

## 8. 测试计划与验收门槛

### 8.1 离线和 UI

继续运行仓库 `npm test`、`npm run test:ui`；涉及窗口/按钮的变更保留原生保护检查，不增加独立未保护窗口。增加少量针对实际风险的回归：

- 统一口述策略覆盖极速/标准、手动/语音；“怎么设计”不自动变长，显式详细与代码题不被切断。
- 三域切换、刷新与重启；切换中旧 token/旧检索迟到不污染新答案；同问题不同域缓存分开。
- 工作区重复导入不增卡，来源 hash 校验；源代码片段不因替换事实丢失；旧手动长文本不会覆盖新指标。
- “没测过这个消融”不变成“没跑 benchmark”；AI 建议不当本人发言；角色修订回撤账本。
- “消融/骁龙”“harness/行业”有上下文纠错，无上下文不误改；React 前端与 ReAct Agent 不混淆。
- 明文题目、答案、请求与原始失败长期可读；仅 credential 字段处理，普通长数字/姓名/项目文本完整。

### 8.2 真实模型验收

先使用 `data/interview-review.json` 的 41 个真实输出点建立开发回归。每个点保留当时原问题、此前真人上下文、旧 CUE 建议和时间；**旧建议与参考答案只给裁判，不给被测模型当事实**。回放到每个时间点停止，禁止读取后续发言偷看答案。完整原 TXT 是审计原件，规范化事件由适配器生成并记录修订。

再准备不少于 24 个未见题：Arclight/cae/八股各8，覆盖新表述、否定、数字追问、复合条件。其中至少6组跨模式/跨话题多轮，12组语音事件边界测试；来源不直接复制主答示例。题目冻结后再运行，修过的题归开发回归，不继续称未见题。

最小完整生成量：`(41 + 24) × 2供应商 × 2重复 = 260` 条；极速/标准在测试中平衡分配，每个供应商每题至少覆盖一种档位，关键故障另补交叉档位。不同会话可并发，同会话按原序；演员/裁判/重试额外调用单独记账。先跑12条烟测，明显错误先修，不直接浪费260条。

| 维度 | 门槛 |
|---|---|
| 默认长度 | 普通口述≤260字符且完整；达标率≥95%，其余逐条列原因 |
| 格式 | 1–3点、短标签、每点1–2句；不要靠删除句号规避 |
| 切题 | 第一有效句直接回应当前问，语义审阅≥95% |
| 术语 | 不堆名词；抽象题给简短例子，不能为了例子编历史 |
| 项目/指标 | 核心九指标绑定正确；零跨项目指标、零把方案说成已测 |
| 事实冲突 | 正常供给指标卡时不得否认 SWE 声明；不为追随本人口误改写真实源码 |
| 角色和修订 | 全部定向回归通过；待确认发言不得当已确认承诺 |
| API与完整性 | 未调用/Mock/仅裁判都不算生成通过；截断与失败保留 |
| 可读性 | 匿名可打开每个 case 的题目、答案、证据、裁判，不需解密 |

自动检查只负责格式、范围、缺字段和计时，语义裁判检查切题/来源/遗漏。所有失败、数字题和不少于20%的自动通过由 Codex 对照来源逐条复查；不能用关键词出现就判答对。重复两轮不是可信置信区间，报告时不要夸大泛化。

## 9. 交付定义

交付代码提交/PR和main状态、可用 workspace/facts、最新版逐点击使用说明、完整明文结果索引、修改前后逐题对照、真实未达标项、精确命令和模型配置来源。说明实际 Windows 检查范围，离线测试不能代替麦克风/声卡实测。

先修 P0（输出、域、指标与角色、明文），再补 P1（故事/实验和延迟），最后测。不得只交“已优化 Prompt”或只有汇总分数。若某家 API 的凭据/配额确实不可用，完整完成另一家的验证并明确缺项；不要伪造两家均通过。
